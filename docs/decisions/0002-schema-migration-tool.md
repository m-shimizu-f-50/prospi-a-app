# ADR-0002: DBスキーマ管理にFlywayを採用する

- 日付: 2026-08-12
- ステータス: 承認済み

## コンテキスト

[05_database_design.md](../05_database_design.md)で `players` / `records` / `record_player_stats` のテーブル構造・制約(型、NULL許容、`UNIQUE(record_id, player_id)`のような複合ユニーク制約、`ON DELETE CASCADE`等)を事前に厳密に設計した。この設計を、実際のMySQLに**意図通り正確に反映させる方法**を決める必要がある。

また、[01_current_analysis.md](../01_current_analysis.md)で指摘した通り、現行アプリ(Laravel)では「マイグレーションファイルでスキーマ変更履歴を管理する」という仕組み自体は妥当だったが、**マイグレーション(実際のDB)とモデル定義(コード側の期待)が食い違う**という不具合が多発していた。同じ失敗を繰り返さない管理方式にしたい。

## 検討した選択肢

1. **Hibernate(JPA)の`ddl-auto`に任せる**(`update`または`create`) — エンティティクラス(Javaのコード)からHibernateが自動でテーブルを生成・変更する。追加ツール不要ですぐ動かせるのがメリット。一方で、複合ユニーク制約やカスケード削除の挙動を細部まで意図通りに制御しづらく、エンティティを変更するたびにHibernateが「暗黙に」テーブルを変更するため、**今のスキーマが実際どうなっているかをコードだけから正確に把握しづらい**
2. **Liquibase** — Flywayと並ぶ代表的なマイグレーションツール。XML/YAML/JSON形式の変更定義(changelog)が中心で、生SQLも書けるが標準的な書き方ではない。機能は豊富だが、学習コストがFlywayよりやや高い
3. **Flyway** — バージョン管理された生SQLファイル(`V1__xxx.sql`のような命名)を積み重ねてスキーマを変更していく。Spring Bootに標準統合されており(`spring-boot-starter-flyway`を入れるだけで自動設定される)、書くものは素のSQLなのでDB設計の学習にも直結する

## 決定

**Flywayを採用する。**

- マイグレーションファイルは `backend/src/main/resources/db/migration/` 配下に `V{バージョン番号}__{説明}.sql` の形式で置く
- Hibernate側は `spring.jpa.hibernate.ddl-auto: validate` に設定し、**テーブルの作成・変更は一切Hibernateにさせない**。Hibernateの役割は「エンティティクラスの定義と、Flywayが作った実際のテーブル構造が一致しているかを起動時に検証するだけ」に限定する

## 却下した理由・トレードオフ

- **`ddl-auto=update`を却下した理由**: [05_database_design.md](../05_database_design.md)で決めた複合ユニーク制約やカスケード削除を、Hibernateの自動生成ロジックが意図通り再現する保証がない。また「エンティティを変更したら暗黙にスキーマも変わる」という状態は、まさに現行アプリで発生していた「コードとDBの不整合」と同じ性質のリスクを生む
- **Liquibaseは不採用(却下ではなく非選定)**: 悪い選択肢ではないが、[05_database_design.md](../05_database_design.md)は既にSQL相当のテーブル定義として書かれており、それをそのままSQLファイルに落とし込めるFlywayの方が学習の遠回りが少ない

## 影響

- 今後のスキーマ変更は、必ず新しいFlywayマイグレーションファイルを追加する形で行う(**一度適用したマイグレーションファイルは変更しない**。変更したい場合は新しいマイグレーションで対応する)
- エンティティクラスとマイグレーションの内容が食い違うと、`ddl-auto: validate` によりアプリ起動時にエラーとして検出される(不整合を早期に発見できる)
- この決定は [08_tasks.md](../08_tasks.md) のT2(DBマイグレーション基盤+初期スキーマ作成)から参照される
