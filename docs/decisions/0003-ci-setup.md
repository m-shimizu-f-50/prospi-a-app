# ADR-0003: CI(GitHub Actions)の導入方針

- 日付: 2026-08-17
- ステータス: 承認済み

## コンテキスト

[08_tasks.md](../08_tasks.md)の未決定事項に「CI(自動テスト・Lint)をどのタイミングで導入するか」とあった。T4(選手API実装)でコード量が増える前に、壊れたコードが混入しないようチェックする仕組みを整えておきたい。

このプロジェクトの開発フローは、`develop`に直接コミットし、ある程度まとまった時点で`develop`→`main`のPull Requestを作成してマージする、というものである(CD=自動デプロイは、クラウドデプロイ先が未定のため対象外。[07_architecture.md](../07_architecture.md) 7章)。

## 検討した選択肢

### CIツール
1. **GitHub Actions** — リポジトリが既にGitHubでホストされており、追加の外部サービス登録なしに`.github/workflows/`だけで使える
2. CircleCI / GitLab CI等の外部サービス — 機能は同等だが、別サービスへの登録・連携設定が別途必要

### 実行タイミング
1. **`develop`/`main`へのPull Request作成時のみ** — 無駄な実行を減らせる。特に「`develop`→`main`のPRのタイミングで、mainに昇格させて良いか確認する」という現在の開発フローと自然に合致する
2. Pull Requestに加えて`develop`への直接pushでも実行 — 日々のコミットのたびに即座にフィードバックを得られる一方、`develop`への直接コミットが多い現状の運用では実行回数が大きく増える

### バックエンドのLintツール
1. **Checkstyle(Google Java Style準拠)** — Javaで標準的な静的解析ツール。命名規則・フォーマット・Javadocの有無まで機械的にチェックできる
2. Lintは導入せず、まずビルド確認のみ — 導入コストは低いが、コードスタイルのブレを防げない

## 決定

- CIツールは**GitHub Actions**を採用する(`.github/workflows/ci.yml`)
- 実行タイミングは**`develop`/`main`へのPull Request作成時のみ**とする
- バックエンドのLintは**Checkstyle(`google_checks.xml`)**を採用する

## 却下した理由・トレードオフ

- **外部CIサービスを選ばなかった理由**: GitHub Actionsで要件を満たせる以上、別サービスへの登録・シークレット管理を増やす必要がない
- **「pushでも実行」を選ばなかった理由**: 現在の開発フローは`develop`への直接コミットが中心であり、そのたびにCIを回すと実行コストが増える。「`main`に昇格させる前に検証する」という現状の運用と一致する、PRトリガーのみの構成にした
- **Checkstyleの導入コスト**: Google Java Styleは「全public型・メソッドにJavadoc必須」など個人開発には厳格すぎる面がある。無効化する選択肢もあったが、[CLAUDE.mdの「可読性を最優先」]方針とも合致するため、ルールは維持しコード側で対応する方針とした(詳細は[09_ci_cd.md](../09_ci_cd.md)参照)
- **副作用**: PRトリガーのみのため、**`develop`への直接コミットではCIが実行されない**。バグの検知は「`develop`→`main`のPRを作るタイミング」まで遅れる

## 影響

- 新機能のコードは`develop`に直接コミットする通常運用のままでよいが、CIの動作を都度確認したい場合は一時的にフィーチャーブランチ+PRを使う必要がある(通常運用への影響はない)
- バックエンドのテストは`@SpringBootTest`でアプリケーションコンテキストを起動するため、CI実行環境にもMySQLが必要になる。GitHub Actionsの`services`機能で一時的なMySQLコンテナを用意する(詳細は[09_ci_cd.md](../09_ci_cd.md))
- 設定の詳細・トラブルシューティングの記録は[09_ci_cd.md](../09_ci_cd.md)に記載する
