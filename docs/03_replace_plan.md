## 1. 残す機能・考え方

現行実装のうち、動作していた/設計思想として妥当だったものは踏襲する。

| 項目 | 踏襲する理由 |
|------|-------------|
| 選手一覧取得・新規登録 | 実際に動作していた数少ない機能。データ項目(打者/投手別ステータス、特能)もゲーム仕様に基づくもので妥当 |
| 「コンテナ(大会) + 選手ごとの成績」の2階層データモデル | [02_requirements.md](./02_requirements.md) 5章で合意した通り、ランク戦(1コンテナ=1試合)・ルーム戦/大会(1コンテナ=1イベント)のどちらも表現できる骨格として有効 |
| 大会詳細を1回のAPIで取得する設計(`/tournaments/{id}/details`相当) | フロントの読み込み効率がよく、TanStack Queryとの相性も良い |
| TanStack Query によるキャッシュ管理、axios-case-converter による snake/camel 自動変換 | 現行フロントで機能しており、Spring Boot移行後も踏襲可能 |
| 4タブのナビゲーション構成(トップ/選手一覧/ランク・ルーム戦/大会) | 画面設計のたたき台として有効。ただし中身は作り直しが必要 |
| 特能・弾道・ポジション等のマスタ定数(`constants/common.ts`) | ゲーム仕様に基づく固定値のため、そのまま利用可能 |

## 2. 削除する機能・コード

スキーマ不整合や未実装により、実質機能していない・矛盾しているものは削除し、新設計でやり直す。

| 項目 | 削除理由 |
|------|---------|
| `PlayerStat`(単数)モデル | `PlayerStats`(複数)と同一テーブルを指す重複モデル。責務が分散する原因だったため統合・削除 |
| `bulkUpdatePlayerStats` 内の存在しないカラムへの書き込み(`games`, `draws`, `win_rate`, `innings`, `strikeouts`, `whip`, `average`) | DBスキーマに存在せず、実行時エラーの原因。新スキーマ・新ロジックで作り直す |
| `PlayerStatsController` を参照するルート一式(統計API・個別成績API) | コントローラー自体が存在せず未実装。新しい分析要件(4章)に合わせて設計しなおす |
| 大会の `start_date` / `end_date` / `description` に関するバリデーション・fillable定義 | マイグレーションに存在しない/削除済みのカラムを扱っており不整合。新スキーマで必要性を再検討する |
| 大会タイプの現行定義(`rank`/`tournament` および `rank_battle`/`cup`/`league`の二重定義) | どちらも実際の要件(ランク戦/ルーム戦/大会)と一致しないため破棄し、新定義に置き換える |
| フロントの壊れた参照(未定義の`API_BASE_URL`、存在しない`createTournament`/`updatePlayerStats`のimport) | ビルド・実行時エラーの原因。作り直す |
| Laravel Sanctum(認証)一式 | 現状ログイン画面がなく実質未使用。[02_requirements.md](./02_requirements.md) 6章の通り、いったん外し、将来フェーズでSpring Securityベースに再設計する |
| 選手一覧ページ(`players/page.tsx`)・トップページの現行実装 | 中身がほぼプレースホルダーのため作り直す |

## 3. 新規追加機能

### 3.1 要件定義で確定した機能

| 機能 | 概要 |
|------|------|
| ランク戦記録(1試合単位) | 試合ごとに使用したオーダーと、出場選手個別の成績(打者: 打数・安打・二塁打・三塁打・本塁打・打点、投手: 勝敗・セーブ)を記録 |
| ルーム戦の種別 | 現行には無かった第3の大会種別。大会と同じ構造(1コンテナ+現在オーダーの上書き編集)で記録 |

## 4. 改善ポイント

機能追加とは別に、実装・設計の質として改善する点。

1. **スキーマとコードの整合性を最初から担保する**: マイグレーション・モデルの`$fillable`・バリデーションを常に一致させる(現行で発生していた不整合の再発防止)
2. **APIをRESTfulに統一する**: `/players/create` のような動詞入りパスを廃止し `POST /players` に統一する(CLAUDE.mdの方針に準拠)
3. **フロントの画面コンポーネントを責務分離する**: 現行の `rank/page.tsx`(1064行)・`tournaments/page.tsx`(890行)のような、UI・状態管理・API呼び出し・計算ロジックが同居する巨大コンポーネントを避け、機能単位で分割する
4. **型定義とAPIレスポンスを一致させる**: UI用の型に「APIから来ないため常に0で初期化される」ような形骸化した項目を作らない
5. **大会種別・ステータス値などのマスタ定義を一箇所で管理する**: 現行のように同じ概念(大会タイプ)がモデルとDBコメントで別々に定義される状態を避ける

## 5. 優先順位(フェーズ分け)

| フェーズ | 内容 | 狙い |
|---------|------|------|
| **P0(MVP)** | 選手管理CRUD(一覧/登録/詳細/更新/削除)、大会マスタ(ランク戦/ルーム戦/大会の3種別)のCRUD、ランク戦の1試合記録(オーダー+個別成績)、ルーム戦・大会の記録(現在オーダーの上書き編集) | 「記録が正しく残せる」状態を最優先で作る。詳細は6章参照 |
| **P1** | 選手起用の分析・比較機能(成績推移グラフ、選手比較、ランキング/フィルタ、ダッシュボード)、効率化機能(オーダーテンプレート保存、スクリーンショット添付、選手検索・オートコンプリート) | 記録がある程度貯まった前提での判断支援と、日常的な記録の手間削減 |
| **P2** | フロントの保守性改善(巨大ページのコンポーネント分割、型整理)、LINE連携+画像解析による自動入力 | 機能が一通り揃った後の品質向上と、難易度の高い自動化機能への挑戦 |
| **P3** | 認証機能 | 学習目的の独立フェーズ。コア機能を止めないよう別PRで実施 |

## 6. MVP(Minimum Viable Product)

### 目的
「記録が正しく残せる」ことを最優先とし、現行アプリで壊れていた核となる機能を、まず正しく動く状態にする。

### MVPスコープに含むもの
- 選手管理: 一覧・登録・詳細・更新・削除(全CRUD)
- 大会マスタ: ランク戦/ルーム戦/大会の3種別での作成・一覧・詳細・削除
- ランク戦記録: 1試合ごとに、出場選手とその試合の個別成績(打者・投手それぞれ)を記録
- ルーム戦・大会記録: 1コンテナに対する現在のオーダーと成績の記録・上書き編集
- 上記に対応する最低限の画面(一覧表示・登録/編集フォーム。デザインの作り込みは含まない)

### MVPスコープに含まないもの
- 選手起用の分析・比較機能、効率化機能(3.2、P1で対応)
- LINE連携・画像解析(3.3、P2で対応)
- フロントのコンポーネント分割等のリファクタリング(P2で対応)
- 認証・ログイン機能(P3で対応)
- オーダー変更履歴の保持(要件定義で「不要」と確定済み)
- 大会参加選手のロースター制限(要件定義で「設けない」と確定済み)

### MVP完了の判断基準(たたき台)
- 選手をアプリ上で登録・編集・削除できる
- ランク戦を1試合分記録し、そこで使った選手ごとの成績が保存・参照できる
- ルーム戦・大会を作成し、オーダーと成績を記録・編集できる
- 上記がSpring Boot + MySQL + Next.jsの新スタック上で一通り動作する
