# API設計レビュー

CLAUDE.mdの「APIはRESTfulに設計する」方針に基づき、エンドポイント設計を以下の観点でレビューする。指摘は理由とセットで提示し、決定はユーザーに委ねる(答えを勝手に決めて実装しない)。

## チェック観点

### 1. リソース設計
- パスは名詞(複数形)で表現されているか。動詞を含むパス(`/players/create`, `/players/1/update` 等)は避け、HTTPメソッドで操作を表現する(`POST /players`, `PUT /players/1`)
- 本プロジェクトの旧実装では `/players/create` のような動詞入りパスが問題として指摘済み(docs/01_current_analysis.md参照)。同じパターンを繰り返さないか確認する
- 階層は意味のあるリソース関係のみにする(例: `/tournaments/{id}/players`)。3階層を超えるネストは避け、必要ならトップレベルリソース+クエリパラメータで表現する

### 2. HTTPメソッドの使い分け
- GET: 副作用なし、冪等
- POST: 新規作成(非冪等でよい)
- PUT: リソース全体の置き換え(冪等)
- PATCH: 部分更新
- DELETE: 削除(冪等)

### 3. ステータスコード
- 200 (成功・GET/PUT/PATCH)、201 (作成成功、Locationヘッダ推奨)、204 (成功・レスポンスボディなし)
- 400 (バリデーションエラー)、401/403 (認証・認可)、404 (存在しないリソース)、409 (競合)、500 (サーバエラー)
- 成功/失敗のレスポンス形式が全エンドポイントで統一されているか

### 4. リクエスト/レスポンス設計
- クエリパラメータ(絞り込み・ソート・ページネーション)とパスパラメータ(リソース特定)が適切に使い分けられているか
- 一覧取得のページネーション方針が決まっているか(未決定ならユーザーに質問する)
- axios-case-converterでsnake/camel変換される前提のため、レスポンスキーはJava側の慣習(camelCase)のままで問題ない(docs/03_replace_plan.md参照)

### 5. ドキュメントとの整合
- 設計した内容は `docs/06_api_design.md`(未作成なら新規作成)に反映されているか。CLAUDE.mdの「docsを更新してから実装」に従い、実装前にdocsへ書き出す

## 進め方

1. 対象のエンドポイント(既存コード、またはこれから作る設計)を確認する
2. 上記観点で問題点を洗い出し、それぞれ「なぜ問題か」「代替案」をセットで提示する
3. 重要な設計判断(選択肢が複数あった場合など)は [adr-writer](../adr-writer/SKILL.md) スキルでADR化を検討する
4. 修正方針はユーザーと合意してから、docsとコードに反映する
