# ADR (Architecture Decision Record) 作成

## 目的

このプロジェクトでは「設計を優先」「勝手に仕様を変更しない」という方針のもと、重要な設計判断は都度 `docs/decisions/` に記録する。ADRは学習記録も兼ねる。なぜその選択をしたか、他にどんな選択肢があったかを言語化することで、後から見返して設計判断の理由を追える状態にする。

## いつ書くか

後から「なぜこうしたんだっけ」と迷いそうな判断があったときに書く。

- 複数の実現方法があり、どれかを選んだとき(例: 認証方式、データモデルの構造、状態管理ライブラリの選定)
- 一度決めた方針を後から変更したとき(変更理由と、旧方針が何だったかを残す)
- CLAUDE.mdの方針(RESTful設計、責務分離など)と現実の要件がぶつかり、トレードオフの上で判断したとき

軽微な実装の詳細(変数名の付け方など)はADR化しない。

## ファイル配置・命名

`docs/decisions/NNNN-slug.md` の形式で作成する。

- `NNNN` は4桁の連番。既存の `docs/decisions/` 内のファイルを確認し、最大値+1を採番する(存在しなければ `0001` から)
- `slug` は英語kebab-caseで、決定内容を短く表す(例: `0001-auth-method.md`)

## テンプレート

```markdown
# ADR-NNNN: <タイトル>

- 日付: YYYY-MM-DD
- ステータス: 提案中 / 承認済み / 却下 / 廃止(supersede先: ADR-XXXX)

## コンテキスト

(なぜこの意思決定が必要になったか。背景・制約・関連する要件)

## 検討した選択肢

1. **選択肢A** — 概要とメリット・デメリット
2. **選択肢B** — 概要とメリット・デメリット
3. ...

## 決定

(採用した選択肢と、選んだ理由)

## 却下した理由・トレードオフ

(採用しなかった選択肢を却下した理由。採用した選択肢が持つデメリット・将来の制約)

## 影響

(この決定によって今後何が制約されるか。覆す場合にどんな条件が必要か)
```

## 進め方

- ADRの中身(選択肢・トレードオフ)はユーザーと一緒に埋める。決定そのものを勝手に下さない。CLAUDE.mdの「不明点は質問する」「勝手に仕様を変更しない」に従い、選択肢を提示した上でユーザーに決定してもらう
- 既存のADRと矛盾する新しい決定をする場合は、古いADRのステータスを「廃止」にし、`supersede先` に新ADRの番号を記載する
