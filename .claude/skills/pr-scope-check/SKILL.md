# PRスコープチェック

CLAUDE.mdの「1PR = 1機能」ルールに基づき、現在の変更(`git diff` / `git status`)が単一の目的に収まっているかを確認する。

## チェック手順

1. `git status` / `git diff` で変更ファイル一覧と差分内容を確認する
2. 変更を目的単位でグルーピングする。例:
   - 機能A追加 / 機能B追加(別機能)
   - バグ修正 / リファクタリング / 新機能追加(性質が異なる変更)
   - フロントエンド(Next.js) / バックエンド(Spring Boot)の変更が、本当に1つの機能のために対になっているか、それとも別々の目的か
   - 設計ドキュメント(docs/)の更新と、無関係な実装変更が混ざっていないか
3. グループが2つ以上に分かれる場合、以下を提案する
   - コミットを分ける(同一PR内で複数コミットにする)べきか
   - ブランチ・PR自体を分けるべきか
   - 分ける場合、どのファイルをどちらに振り分けるか

## 判断の目安

- 「一緒にレビューされないと意味が分からない変更」は同一PRでよい(例: APIエンドポイント追加とそれを呼ぶフロント実装)
- 「片方だけでも独立してレビュー・マージできる変更」は分割候補
- 迷う場合は分割する方向で提案する。小さいPRの方がレビューしやすく、学習用途としても1つずつ設計判断を追いやすいため

## 進め方

- 分割が必要と判断したら、具体的なコミット分割案(どのファイルをどのコミットに)を提示する
- 実際にコミットを分ける作業(`git add -p` 等)はユーザーの合意を得てから行う
- コミットメッセージ・PR説明文のフォーマットは [commit-pr-conventions](../commit-pr-conventions/SKILL.md) スキルに従う
